# PHP2Shell（CVE-2026-109618）とは？脆弱性対策が必要な理由を歴史から学ぶ【初心者向け】

## はじめに：PHP2Shellで何が起きたのか

2026年10月21日、プログラミング言語PHPの重大な脆弱性2件（CVE-2026-109618、CVE-2026-109619）について、修正版が公開されました。この2件は「PHP2Shell」と呼ばれ、認証なしで、外部からサーバー上のプログラムを実行されるおそれがあります。深刻度を示すCVSS v4.0のスコアは、どちらも9.2で、最も高い区分の「緊急」にあたります。

攻撃の試みが世界的に急増するなか、日本国内でも、銀行、ゲーム、EC、自治体などのサービスで、緊急メンテナンスや一時停止が相次いだと報じられました。

## PHP2Shell（CVE-2026-109618/109619）とは：影響範囲・修正版・経緯

![PHP2Shellの1週間](https://static.zenn.studio/user-upload/687a0b1e9b7c-20261025.png)

| 項目 | 内容 |
| --- | --- |
| **対象** | PHP 5.4から8.5.11まで。Webリクエストを処理するPHP環境全般で、PHP-FPM、Apacheのmod_phpなども含まれる |
| **修正版** | PHP 8.5.12、8.4.27、8.3.36、8.2.35 |
| **PHP 7.4〜8.1** | 公式の修正版リリースは出ない（サポート終了）。PHPのセキュリティチームが、ソースからビルドする人向けの最小限の修正（バックポート）を公開している。パッケージで入れている場合は、ディストリビューションやLTS提供元の更新を確認する |
| **PHP 5.4〜7.3** | 修正は提供されない。新しい版への移行が必要 |
| **更新できない場合** | CISAなどは、更新できるまで該当システムをインターネットから切り離すことも勧めている（Tenableの解説による） |
| **経緯** | 10月20日にPHP開発チームが緊急リリースを予告し、同じ日に脆弱性の詳細が予定より早く外部に漏れた。21日の日本時間23時に修正版が公開された |
| **攻撃の状況** | 公表の4日前の10月17日に、Amazonが攻撃試行を記録した。Cloudflareの観測では、公開後45分以内に数万件、22日早朝には数百万件に達した |
| **追加情報** | 10月23日、特殊なセッション設定の場合のみ影響を受ける別の脆弱性（CVE-2026-115560）についても、PHPが注意喚起を出した。現時点で悪用は報告されていない |

今回の特徴は、**情報が先に漏れ、攻撃が先に始まり、修正の適用があとを追う**形になっていることです。さらに、サポートが終わった古いバージョンには修正が出ません。

## なぜ脆弱性対策が必要なのか

脆弱性とは、ソフトウェアに潜む、悪用できてしまう欠陥のことです。

厄介なのは、次の3点です。

- 自分が書いたコードだけでなく、**使っているライブラリや言語にも**潜んでいる
- 見つかった時点で、**世界中の攻撃者も同じ情報を手にする**
- 修正版が出ても、**適用しない限り穴は開いたまま**

自動車のリコールで考えてみましょう。たとえば、メーカーから「ドアの一部を押し込むとロックが解除され、誰でも自由に運転できてしまう欠陥があったので、無料で直します」と通知が届いたとします。それでも持ち主が修理に出さず走り続ければ、いつか盗難に遭う可能性が出てしまいます。

ソフトウェアも同じです。ただし、現実の泥棒と違って、攻撃者は機械的に世界中のサーバーを調べて回ります。通知が出た日から、泥棒が街中の車のドアを片っ端から試し始めるようなものです。PHP2Shellでも、修正版の公開から45分以内に、数万件の攻撃の試みが観測されたと報告されています。

こうした被害を受けて、対策の仕組みは少しずつ変わってきました。

## 脆弱性対策の歴史（1988〜2021年）

### 1988年：モリスワーム ― インターネット最初の大事件

研究者同士が信頼し合う小さな世界だったインターネットに、初めて「防御」の必要性を突きつけた事件でした。

1988年11月2日、大学院生のRobert Morris氏が作ったワーム（自分でコピーして広がるプログラム）がインターネットに放たれました。UNIXのfingerdというサービスの弱点などを利用して広がり、感染した機械は動作が重くなって使い物にならなくなりました。

被害台数は「約6,000台」とよく言われますが、これはMITでの感染率から全体を推定した数字で、正確な台数は分かっていません。

#### 仕組み：バッファオーバーフロー

fingerdの弱点は、「バッファオーバーフロー」と呼ばれる種類の欠陥でした。プログラムは、データを入れる「箱」（バッファ）の大きさを決めてメモリに確保します。ところが、箱より長いデータを受け取ったときの確認が甘いと、あふれたデータが**となりのマスを上書き**してしまいます。

![バッファオーバーフローの仕組み](https://static.zenn.studio/user-upload/8596dd2977c9-20261025.png)

対策はシンプルで、**入れる前に長さを確認する**ことです。たとえば箱が8マスなら、データを入れる前に「長さは8マス以内か」を調べ、9マス目以降は受け付けない（断る）ようにします。fingerdは、512バイトの箱に、長さを確認しない読み込み関数（gets）で入力を入れていたため、長すぎる入力があふれました。

いまは、長さを自動で確認してくれるプログラミング言語（PythonやJavaなど）やライブラリを使うことも、有効な対策の一つです。

> **変わったこと**：事故が起きたときの**連絡・調整の窓口**として、同じ月にCERT/CCが設立されたとされています。「各自で何とかする」から「組織で対応する」への第一歩でした。

### 1998〜2000年：Webアプリの脆弱性に名前がつく

Webが広まり、Webならではの欠陥が見つかり、「名前」がつきました。

| 脆弱性 | 時期 | 何があったか |
| --- | --- | --- |
| **SQLインジェクション** | 1998年12月25日 | ハッカー誌Phrackの54号で、Jeff Forristal氏（rain forest puppy名義）が、この種の問題を初めて公に解説した。当時は、この名前では呼ばれていなかった |
| **クロスサイトスクリプティング（XSS）** | 2000年1月 | Microsoftのセキュリティ技術者たちが議論の末に名前を採用し、2月初めにCERTと共同で勧告を出した |

#### 仕組み：データが「命令」になってしまう

この2つに共通するのは、**お客さんが入力した「データ」が、プログラムにとっての「命令」として扱われてしまう**点です。

たとえば、注文書の「備考欄」に「全部タダにして」と書いたら、店員がそれを「指示」だと思って実行してしまった、というイメージです。

![インジェクション攻撃の仕組み](https://static.zenn.studio/user-upload/f729f4a443ec-20261025.png)

SQLインジェクションはデータベースで、XSSはブラウザの画面で起きる違いはありますが、考え方は同じです。対策も共通していて、**「命令」と「データ」を分けて渡す**ことが基本になります。

> **変わったこと**：欠陥の種類に**名前**がつき、世界中で同じ言葉を使って対策を語れるようになりました。

### 1999〜2003年：共通の言葉とチェックリストの登場

脆弱性に共通の「番号」が付き、「危険度ランキング」も作られた時期です。

| 年 | できたもの | 内容 |
| --- | --- | --- |
| 1999年 | **CVE** | MITREが、脆弱性に共通の識別番号を付ける仕組みを公開した。公開当初は321件で、2026年7月末時点では約35万件（第三者の集計）。「CVE-年-番号」で、バラバラだった呼び名がそろった |
| 2001年 | **OWASP** | Webアプリのセキュリティを高める非営利コミュニティ。9月9日にMark Curphey氏が始めた |
| 2003年 | **OWASP Top 10** | 「最も重大なWebアプリのリスク」をまとめたリストが初めて公開された。以降も更新され、開発現場の共通のチェックリストとして使われている |

> **変わったこと**：脆弱性に**番号**が、対策に**チェックリスト**ができて、組織として対策を進めやすくなりました。

### 2002〜2003年：Slammerと月例パッチ ― 修正の「配り方」が変わった

修正版が出ているのに、適用が追いつかない。この問題は、2000年代のはじめに、ワームの大流行という形で表れました。

| 時期 | 出来事 | ポイント |
| --- | --- | --- |
| 2001年 | Code Red・Nimda | 修正版がすでに出ていた脆弱性を突いて、数時間で数十万台に広がったとされる |
| 2003年1月25日 | SQL Slammer | SQL Serverの脆弱性（MS02-039）を突いた。修正版は約6か月前の2002年7月に公開済みだったが、多くの組織が未適用だった。10分ほどという推定の短時間で広がり、ネットワーク障害を起こした |

#### 変わったのは「配り方」

それまでMicrosoftの修正プログラムは、準備ができ次第、バラバラに公開されていました。管理者にとっては、いつ何が来るか分からない状態でした。

2003年10月、Microsoftは**修正プログラムを毎月1回まとめて公開する**ことを発表しました。最初の公開は10月14日で、これが「Patch Tuesday（月例パッチ）」です。「毎月この日に来る」と決まれば、組織はその日に合わせて、検証や適用の準備ができます。

> **変わったこと**：修正版を「出す側」だけでなく、**「受け取って適用する側」を助ける仕組み**ができました。

### 2014年：Heartbleed ― 基盤ソフトの小さなバグが世界に波及

ソフトの土台になる部品の、たった1つの確認漏れが、世界中のサーバーに影響しました。

2014年4月、暗号化通信（HTTPS）を支えるOpenSSLに「Heartbleed」（CVE-2014-0160）が見つかりました。2012年に混入していたバグで、4月1日に報告され、7日に修正版と同時に公表されました。

#### 仕組み：「長さの申告」を信じすぎた

このバグは、オウム返しのような機能にありました。「HAT」と送って「3文字返して」と頼めば、サーバーは「HAT」を返します。ところが、「HAT」だけ送って「500文字返して」とうその長さを申告すると、バグのあるサーバーは**申告を信じて、実際の長さを確認せず**、となりにあるメモリの中身まで返してしまいました。

![Heartbleedの仕組み](https://static.zenn.studio/user-upload/b1f2f09b0546-20261025.png)

メモリには、パスワードや秘密鍵などが入っていることがあります。修正版が出た後も、6月の時点でなお約30万台の公開サーバーが脆弱なままでした。

**どんなに堅牢なソフトでも、土台の部品が穴になれば全体が危うくなる**ことを、世界が実感した事件でした。

> **変わったこと**：2014年4月、Linux Foundationが**Core Infrastructure Initiative**を発足させました。Amazon、Google、Microsoftなどの企業が支援に加わり、世界中が使う基盤ソフトを資金面で支える動きが始まりました。OpenSSLは当時、専任の開発者が1人しかおらず、年間収入が100万ドルを超えたことがない状況だったと報じられています。

### 2017年：修正はあったのに適用されなかった

この年は、大きな事件が2つ起きました。

![2017年の時間差](https://static.zenn.studio/user-upload/8f64f7e52275-20261025.png)

**Equifax（アメリカの信用情報会社）**

| 日付 | 出来事 |
| --- | --- |
| 2017年3月7日 | Apache Struts（CVE-2017-5638）の修正版が公開された |
| 3月10日 | Equifaxが修正を適用しないまま、最初の侵入があったと報じられている |
| 5月13日ごろ | 本格的に情報が持ち出され始め、約2か月半、気づかれなかった |
| 7月29日 | Equifaxが侵害に気づいた |
| 9月 | 公表。約1億4,700万人分の情報が漏れた |

**WannaCry（世界中で大流行したランサムウェア）**

| 日付 | 出来事 |
| --- | --- |
| 2017年3月14日 | Microsoftが、MS17-010で脆弱性を修正済みだった |
| 4月14日 | エクスプロイト（脆弱性を突くプログラム）が流出した |
| 5月12日 | WannaCryが世界中で大流行した。被害の多くは、パッチ未適用の組織や、サポートが終了した古いWindowsだった |
| 5月13日 | Microsoftが、サポート切れのWindows XPなどにも緊急パッチを出した |

どちらも、リコール通知が届いていたのに、修理に出さず、盗まれてしまった状態でした。被害を分けたのは「脆弱性の有無」より「直したかどうか」でした。

> **変わったこと**：この2つの事件は、修正版を配るだけでは足りず、**適用させる仕組み**が必要だと示しました。

### 2020〜2021年：「見えない部品」と、悪用されている脆弱性の優先対応

守る対象が、自分のコードから、使っている部品全体へ広がった時期です。

| 出来事 | 時期 | 内容 |
| --- | --- | --- |
| **Log4Shell** | 2021年12月 | Javaのログライブラリで見つかったCVSS 10（最高）の脆弱性。Apacheへの報告は11月24日、修正版の公開は12月9日。最も早い攻撃の痕跡は**公表より前の12月1日**に見つかった |
| **SolarWindsとSBOM** | 2020年〜2021年5月 | 正規のソフト更新に不正コードが混ぜられた事件を受けて、2021年5月に米国で、SBOMを含む対策を求める大統領令14028号が出た |
| **CISAのKEV** | 2021年11月 | 実際に悪用が確認された脆弱性の一覧（KEVカタログ）を作成。連邦政府の民間機関には、期限内の修正を義務づけた。民間企業などにも、優先して対応することが強く勧められている |

#### 仕組み：部品の中の部品

アプリは、フレームワークやライブラリなどの部品でできています。その部品も、さらに別の部品を使っています。自分では選んでいない「孫の部品」に穴があっても、気づきにくいのが問題です。

![見えない部品とSBOM](https://static.zenn.studio/user-upload/b0b996c7fbaf-20261025.png)

そこで注目されたのが、**SBOM（ソフトウェア部品表）** です。食品の原材料表示のように、使っている部品とバージョンを一覧にしておけば、穴が見つかったときに「うちで使ってる？」をすぐ調べられます。

> **変わったこと**：使っている部品の一覧（SBOM）を持つことと、**悪用されている脆弱性から先に直す**ことが、対策の基本になっていきました。

## 歴史を貫く「時間差」

ここまでの節目を並べると、共通点が見えてきます。どの事件でも、修正版が出てから適用されるまでの時間差が、被害の大きさを分けていました。

![脆弱性対策は時間差の戦い](https://static.zenn.studio/user-upload/ef1f43818e6b-20261025.png)

| 事件 | 時間差のポイント |
| --- | --- |
| SQL Slammer（2003） | 修正公開（2002年7月）の約6か月後に大流行した |
| Equifax（2017） | 修正公開から約2か月後に、情報の持ち出しが本格化した |
| WannaCry（2017） | 修正公開から約2か月後に大流行 |
| Log4Shell（2021） | 公表の約8日前から攻撃の痕跡があった |
| PHP2Shell（2026） | 公表の4日前に攻撃試行の記録があった |

「修正版が出てから適用されるまでの時間」を短くすること、そして「公表前から攻撃されることもある」と覚悟しておくことが、現代の対策の核心です。

## AIとSNSが、時間差をさらに縮めている

過去の事件と今とで大きく違うのは、その時間差が縮むスピードです。

**「発見」「悪用」「拡散」のどれもが、年々速くなっています。**

![AIとSNSが時間差を縮めている](https://static.zenn.studio/user-upload/06d45926ad6e-20261025.png)

### ① 発見：AIが「見つける」を速くする

PHP2Shellは、AIを使った調査で見つかったと報じられています。PHPのセキュリティ情報には、Calif社、Wiz社、OpenAIが発見者として挙がっています。別々のチームが数週間の差で同じ欠陥にたどり着いた点も、「見つけやすくなった」ことを示しています。

ただし、AIがどこまで効いたかは慎重に見る必要があります。Calif社は「一般に使えるAIモデルだけを使ったが、PHPの歴史を知っていたことのほうが重要だった」と述べています。AIは人間の専門家を置き換えるというより、**専門家の探索を加速する道具**と考えるのが現実的です。

### ② 悪用：AIが「攻撃コード作り」を速くする

公開された脆弱性から、検証用の攻撃コードを短時間・低コストで作れるという報告があります（CSAの資料が引用する業界レポートでは、10〜15分・約1ドル）。これは業界の報告であり、独立に検証された数字ではありません。それでも、**「修正版が出てから攻撃が始まるまでの猶予」が縮んでいる**傾向は、複数の調査で共通しています。

| 指標 | 内容 |
| --- | --- |
| 攻撃コードが出るまでの平均日数 | 2022年の約32日から、2023年のデータでは約5日へ |
| 公表日かそれ以前に登場した攻撃コードの割合 | 2025年に新たに追跡されたもののうち約32%（VulnCheck） |

調査ごとに集計年や方法が違うため、数字は目安として見てください。

### ③ 拡散：SNS・コミュニティが「広げる」

PHP2Shellでは、詳細が技術系掲示板 Hacker News の投稿をきっかけに漏れたと報じられています。その後、バグが本物であることが確認され、検証用コードがネット上に出回りました。Cloudflareは、修正版の公開の約9時間前に防御ルールを有効にしていましたが、公開後の攻撃試行は翌朝には数百万件に達しました。

昔は、脆弱性の情報は一部の専門家や掲示板の中に留まっていました。今は、**SNSやコミュニティで数時間のうちに世界中へ伝わります**。これは、守る側にとっても情報収集に役立つ一方、攻撃側に「準備の時間」を与えてしまう面もあります。

### だから、守る側も「速さ」を前提にする

猶予が短くなった以上、事件が起きてから慌てるのではなく、備えを先に整えておく必要があります。

AIは守る側も使えます。コードの監査や、更新の優先順位づけにAIを活用する動きも広がっています。**速くなったのは攻撃だけではない**、という点も押さえておきましょう。

## PHPの脆弱性対策：今日からできる5つのこと

歴史が教えてくれるのは、派手な対策よりも、時間差を縮める基本が大切だということです。

![今日からできる5つのこと](https://static.zenn.studio/user-upload/681e9f989558-20261025.png)

| # | やること | 内容 |
| --- | --- | --- |
| 1 | **棚卸しをする** | 自分たちのシステムが、どの言語・バージョン・ライブラリを使っているかを一覧にする（SBOMの考え方） |
| 2 | **サポート期限を確認する** | 使っているバージョンのサポート終了日を把握し、切れる前に計画的に更新する |
| 3 | **更新を急げる体制を作る** | 緊急の修正版を、いつ誰がどう適用するか、あらかじめ決めておく |
| 4 | **情報源を決めておく** | IPAやJPCERT/CC、ベンダーの公式アドバイザリを定期的に確認する |
| 5 | **すぐ更新できない場合の代替策を知る** | 公式が示す緩和策や、利用中のサービス提供元の対応状況を確認する |

全部をいきなりやる必要はありません。まずは①の棚卸しからで十分です。

## まとめ

- 脆弱性対策の歴史は、「窓口をつくる → 名前をつける → 番号とチェックリスト → 修正を月例で配る → 基盤ソフトを支える → 部品と悪用状況まで把握する」と進んできた
- 被害の多くは、**修正版が出てから適用されるまでの時間差**で起きてきた
- AIとSNSの普及で、その時間差はさらに縮まっている

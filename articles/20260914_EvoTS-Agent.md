# 金融時系列の変化点検出を自己進化させるLLMエージェント「EvoTS-Agent」を解説
## はじめに：LLMエージェントが同じ改善を繰り返してしまう理由

LLMエージェントにコードを書かせて何かを最適化させるとき、こんな経験はないでしょうか。

- 一度目の提案は良かったのに、二度目・三度目の「改善」でむしろスコアが下がる
- 何度指示しても、同じアプローチを微修正するだけで根本的に違う方法を試してくれない
- 複数回の試行錯誤の結果、良かったアイデアと悪かったアイデアがバラバラのまま、うまく統合されない

これはまさに、株価や信用スプレッドといった金融時系列データの「構造変化（レジームチェンジ）」を自動検出するAIエージェントが抱えていた課題そのものです。

2026年8月に公開された論文 *"EvoTS-Agent: A Self-Evolving LLM Agent for Financial Time Series Change Point Detection"*（Jiang et al., arXiv:2608.17933）は、この「同じ答えを磨き続けてしまう病」に、明確なルールベースの解決策を提示しました。

## この記事で学べること

- なぜ「変化点検出」が金融データで難しいのか
- 従来のLLMエージェントが陥りがちな3つの罠（停滞・局所最適・知見の分断）
- EvoTS-Agentが導入した「改訂・代替戦略・再結合」という3つの進化オペレータの仕組み
- 「精度が上がった」だけでなく「実行成功率100%」が持つ実務的な意味
- 自分の業務（LLMエージェントによる自動最適化タスク全般）にどう応用できるか

## そもそも「変化点検出」とは何か

変化点検出（Change Point Detection）とは、時系列データの中で「統計的な性質が変わった瞬間」を見つけるタスクです。

- 株のボラティリティが急に高まったタイミング
- 信用スプレッドの平均水準がシフトしたタイミング
- 取引パターンが一変したタイミング

こうした瞬間を検出できると、リスク管理、資産配分、不正検知など、金融実務の意思決定に直結します。

ただし厄介なのは、「万能な検出アルゴリズムは存在しない」という点です。あるデータでは平均値の急激な変化を捉えるのが得意な手法が、別のデータでは変化を見逃す、といったことが日常的に起きます。データごとに前処理・モデル選択・閾値調整を専門家が手作業で行う必要があり、これがスケールしない大きな理由でした。

## 従来のLLMエージェントは何が問題だったのか

論文では、既存のLLMエージェント型アプローチ（DS-Agent、ResearchAgent、TS-Agentなど）が抱える限界を3つに整理しています。

| 問題 | 内容 |
|---|---|
| **繰り返し改訂（Repeated Revision）** | 一度作った解を延々とリビジョンし続け、スコアが頭打ちになっても気づかず改善を続けてしまう |
| **停滞を検知する仕組みがない（No Stagnation-Aware Control）** | 「いつ今のアプローチを諦めて別の方向を試すべきか」を判断する明示的なルールがなく、局所最適に陥りやすい |
| **試行が孤立している（Isolated Trajectories）** | 複数回の実験でそれぞれ良い発見があっても、それらを組み合わせて最終解に反映する仕組みがない |

要するに、「粘り強く改善する」ことはできても、「見切りをつけて方向転換する」「複数の成功体験を統合する」ができていなかったわけです。

## EvoTS-Agentの仕組み

### 全体の流れ

![EvoTS-Agent全体の流れ：タスク&生データ→EDA/メタ特徴量抽出→上位K個の候補モデル選定→ウォームアップ試行(2K回)→検証フィードバックに基づく進化ループ→最良パイプライン](https://static.zenn.studio/user-upload/ee12c6f6bbce-20260914.png)

まず時系列データの統計的特徴（自己相関、トレンドの強さ、非定常性、周期性、局所的な平均・分散の変化量など）を抽出し、EDAと呼ばれるこの工程を通じて、LLMに「この特徴ならどのモデルが向いていそうか」を判断させます。ここでモデルバンク（PELT、Bottom-up、Window、ChangeForest、ベイズ的オンライン変化点検出、KL-CPD、独自のスペクトル手法の計8種）から候補が絞り込まれます。

重要なのは、ここで**最終決定はしない**という点です。EDAはあくまで探索の出発点を絞るためのもので、実際にどのモデルが最適かは、この後の検証ベースの進化ループで決まります。

### 3つの進化オペレータ：改訂・代替戦略・再結合

ここがこの論文のコアアイデアです。エージェントは以下の3つの「型」を、状況に応じて切り替えます。

![3つの進化オペレータの制御フロー：Revisionで改訂を続け、改善が停滞したらAlternative Strategyに切り替え、最終イテレーションで必ずRecombinationを実行する](https://static.zenn.studio/user-upload/b06fce1677e1-20260914.png)

1. **Revision（改訂）**：現在の最良解（incumbent）をベースに、時系列の表現方法・検出器の設定・ハイパーパラメータ・後処理などを一箇所だけ変更して試す。通常運転はこれ。

2. **Alternative Strategy（代替戦略）**：改訂による改善幅（Δscore）が「意味のある改善」の閾値（ε）を下回った（＝停滞した）場合に発動。全く違う検出モデルや、EDAで候補に挙がっていたが未試行のモデルへ切り替える。停滞した試行は「ここはもう掘っても無駄」という**負の証拠**として扱われ、同じ方向への後戻りを防ぐ。

3. **Recombination（再結合）**：探索の最終ステップでのみ発動。それまでに蓄積された高性能な複数のトラジェクトリ（実験履歴）から、それぞれの良い部分を統合して最終解を作る。

#### 補足：改善幅はLLMではなく関数で判定している

ここで気になるのが、「改善したかどうか」を誰がどうやって判断しているのかという点です。結論から言うと、**LLMの主観的な判断ではなく、数式による機械的な計算**です。

論文では、良し悪しを数値で判定するための計算式（評価関数）があらかじめ定義されています。流れを整理すると：

1. LLMが次の実験コードを生成する（ここだけがLLMの仕事）
2. 生成されたコードを実際に実行し、検証データに対して変化点検出を行う
3. 正解の変化点と検出結果を突き合わせて、位置のズレも考慮したF1スコアを**機械的に計算**する（これがq_k）
4. `q_k - q_prev`（今回のスコア − 現在のincumbentのスコア）を計算し、これがεを下回れば「停滞」と判定する

つまり「LLMに前回と今回の結果を見せて『改善したと思う？』と聞く」わけではありません。LLMが関与するのは「次にどんな実験をするか」を考える部分までで、成果の評価自体は再現性のある数値計算に任せています。これが、この後の実務応用の章で触れる「検証用ラベルが必要」という制約にもつながっています。

#### 補足：「良い部分の統合」とは何をしているのか

Recombinationの「良い部分を統合する」という表現も、コードの断片を物理的に切り取って貼り合わせるような処理ではありません。Algorithm 1を見ると、流れは次のようになっています。

1. トラジェクトリプールの中から、高性能だったものを複数選ぶ（`SelectStrongTrajectories`という選択処理。件数は論文中に固定の数値指定はありません）
2. 選ばれた各トラジェクトリの記録（実装コード、コードの差分、LLMによる要約、検証スコア）をまとめてコンテキストとしてLLMに渡す
3. LLMが「現在のincumbentのスクリプトを土台にしつつ、他の有望な試行で発見された工夫を取り込んだ新しいコード」を**改めて生成する**

つまり、複数の実験結果からそれぞれ数行ずつ切り出して機械的に組み合わせるのではなく、**「これまでの成功パターンを踏まえてLLMに書き直させる」**という形の統合です。論文のケーススタディ（Figure 5）でも、「Bottom-Up手法の強みと、それ以前のトラジェクトリが持っていた補完的な証拠を考慮して再結合する」という記述があり、機械的な切り貼りというよりLLMによる統合的な再設計に近いニュアンスで描かれています。

### すべての試行が「記録」される

もう一つ地味に重要なのが、実行したすべての実験（実装コード、検証スコア、コードの差分、要約、親子関係）を「トラジェクトリプール」として記録し続ける点です。これにより、単発の会話履歴ではなく、**探索の系譜が追える構造化されたグラフ**として実験全体を管理できます。

## 客観的なデータで見るEvoTS-Agentの性能

論文では、OUプロセス（信用スプレッドを模した合成データ）、平均・分散シフトデータ、ADIA Lab Structural Break Challenge（実データベース）、Bee-Dance（実世界の行動データ）の4つのベンチマークで評価しています。評価指標はF1スコア・Precision・Recall・Hausdorff距離を用いています（各指標の意味は冒頭の用語集を参照してください）。

### 実行成功率：ここが一番わかりやすい差

EvoTS-Agentは全てのバックボーンLLMにわたって100%の実行成功率を維持しています。一方、比較対象のResearchAgentは、OUデータセットでSonnet-4.6・Sonnet-5を使った場合に成功率が33.3%まで落ち込みました。

![バックボーンLLM別の実行成功率比較（OUデータセット）：ResearchAgentはGPT-5.4で0%、Sonnet-4.6/5で33.3%まで落ち込むのに対し、EvoTS-Agentは全モデルで100%を維持](https://static.zenn.studio/user-upload/1c33f7e9b664-20260914.png)

この成功率は、変化点をどれだけ正確に当てたかとは独立した指標で、エージェントが生成したコードがエラーなく最後まで実行できたかどうかを表します。どれだけ理論上優れたスコアを出せても、3回に2回はコードが落ちて結果すら出ないなら実務では使えません。この安定性は、モデルバンクという「動作確認済みの選択肢」を用意しておくことと、明示的な探索戦略を持つことの副産物として得られています。

### 精度面でも大きな改善（ただし一律ではない）

特に改善が顕著だったのはADIAデータセット（実データ由来）です。GPT-4oバックボーンにおいて：

- F1スコア：TS-Agent 0.235、DS-Agent 0.461 → EvoTS-Agent **0.500**
- Hausdorff距離：TS-Agent 212.0、DS-Agent 130.6 → EvoTS-Agent **14.8**

![ADIAデータセットにおけるF1スコア比較（GPT-4o）：ResearchAgent 0.074、TS-Agent 0.235、DS-Agent 0.461、EvoTS-Agent 0.500](https://static.zenn.studio/user-upload/1b961e91b74f-20260914.png)

![ADIAデータセットにおけるHausdorff距離比較（GPT-4o）：ResearchAgent 238.4、TS-Agent 212.0、DS-Agent 130.6に対し、EvoTS-Agentは14.8と大幅に低い（低いほど良い）](https://static.zenn.studio/user-upload/b1ea4ac79b5a-20260914.png)

Hausdorff距離のグラフを見ると差は一目瞭然です。他のエージェントが100〜240程度のズレを抱えているのに対し、EvoTS-Agentだけが15前後まで縮まっています。

一方で、実世界データであるBee-Danceデータセットでは、GPT-4oバックボーンに限ってはTS-Agentの方がF1・Hausdorff距離ともに優れており、論文でも実世界データセットでは他手法との差がより小さいことが正直に述べられています。

### アブレーション実験：どの要素が効いているのか

「代替戦略」と「再結合」をそれぞれ外した場合の実験（Bee-Dance、GPT-5.4）では：

| 構成 | F1スコア |
|---|---|
| フル構成のEvoTS-Agent | 0.635 |
| Alternative Strategyを除去 | 0.578 |
| Recombinationを除去 | 0.575 |

![アブレーション実験：構成要素ごとのF1スコア（Bee-Dance, GPT-5.4）。フル構成の0.635に対し、Alternative Strategyを除去すると0.578、Recombinationを除去すると0.575まで低下](https://static.zenn.studio/user-upload/6db11327d3e6-20260914.png)

Recombinationを除去するとRecallが0.671から0.602へ明確に低下しており、最終的な統合ステップが複数の試行から得られた補完的な証拠をまとめる役割を果たしていることが示唆されます。つまり、「複数試す」だけでなく「複数の成功パターンを最後にちゃんと合成する」ことが性能向上に寄与しているというわけです。

## LLMエージェント設計への実務応用を考える

この仕組みは変化点検出に限らず、「複数の候補手法があり、検証指標で良し悪しを客観的に測れるタスク全般」に一般化できる考え方です。

- 予測モデルの自動選択・チューニング
- 異常検知パイプラインの自動構築
- 特徴量エンジニアリングの自動探索

いずれも「改訂を繰り返すだけのAutoML」に対して、「改善が止まったら方向転換する」「良かった複数の試行を最後に統合する」というメタ制御を組み込む余地があります。

### ClaudeやGPTを使った自作エージェント設計にも応用できるか

変化点検出に限らず、ClaudeやGPTを使って自作のコーディングエージェントやリサーチエージェントを設計する場合にも、この枠組みは制御構造としてそのまま輸入できます。汎用的に転用できるのは主に次の3点です。

- 「改訂を繰り返して停滞したら、別の方向を試す」というメタ制御ルール
- 「複数の試行結果を最後に統合する」という仕上げのステップ
- すべての試行を実装・スコア・要約・親子関係つきで記録し、次の判断材料にする「トラジェクトリプール」という設計

「Revision→停滞判定→Alternative Strategy→最後にRecombination」という流れは、状態に応じて次の挙動が自動的に決まる仕組みで、専門用語ではステートマシンと呼ばれます。この考え方は変化点検出に限らず、検証可能な評価指標さえ用意できれば幅広いタスクに適用できます。コードのテスト成功率、文章の評価スコア、画像生成の品質スコアなどが評価指標の例として挙げられます。

ただし前提条件があります。先述の通り、改善判定は客観的な数値計算で行う必要があります。ここが曖昧だと「停滞したかどうか」をLLMの主観的判断に委ねることになり、この論文がそもそも解決しようとしていた「判断基準が曖昧」という問題に逆戻りしてしまいます。つまり、**「制御ロジックの設計思想はそのまま使えるが、評価関数は自分のタスク用に別途用意する必要がある」**というのが実際のところです。

ただし実務導入には2つの壁があります。

1. **検証用のラベルデータが必要**：EvoTS-Agentが使う検出器自体は教師なし手法ですが、「どのトラジェクトリを残すか」を判断するためには正解ラベル（過去の既知の変化点など）付きの検証データが必要です。ラベルが手に入りにくい領域では、この枠組みをそのまま持ち込むのは難しいでしょう。

2. **計算コストと時間**：LLMによるコード生成・実行・検証を何度も繰り返す設計のため、リアルタイム性が求められる用途には不向きです。論文自体、実行時間やコストの定量比較を報告していません。

## まとめ

EvoTS-Agentは、金融時系列の変化点検出というニッチなタスクを題材にしていますが、そのアイデアの核心は「LLMエージェントに、いつ深掘りし、いつ見切りをつけ、いつ統合するかを、検証結果に基づいて明示的に判断させる」という点にあります。

- 従来手法の弱点は「粘り強いが柔軟性に欠ける」ことだった
- EvoTS-Agentは検証スコアの停滞を検知して自動的に戦略を切り替える仕組みを導入
- 改善判定はLLMの主観ではなく、F1スコアなど客観的な数値計算で行われている
- 精度だけでなく「実行成功率100%」という信頼性の高さが際立つ結果に
- この制御構造は変化点検出に限らず、評価指標さえ用意できれば自作のLLMエージェント設計にも応用できる
- 実務応用には検証データの確保と計算コストの検討が課題

「AIエージェントに任せっぱなしにしたら、同じ改善を繰り返すだけで停滞した」という経験がある方には、特に参考になる論文だと思います。

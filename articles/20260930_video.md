# 推測より構造化データ — 動画生成パイプラインで学んだAIエージェント設計の勘所

この記事では、Zenn記事から動画・サムネイル・YouTubeショートまでを自動生成するパイプラインの作り方を紹介します。時間削減の話だけでなく、「AIエージェントをどう設計し、どこでつまずき、どう直したか」を中心に書きます。

キーワードは **「推測より構造化データ」** です。AIに推測させるのをやめて、すでに手元にある正確なデータを渡すだけで、不具合の多くが解決しました。

## 動画制作に64時間かかっていた課題とAIによる自動化の動機

エンジニアの仕事が忙しくなってきて、気づいたらYouTubeの更新が止まっていました。Zennの記事も、気がつけば時事ネタのキャッチアップだけになっていました。「これは記事にする価値があるな」と思って書くようなものが減っていました。

一方で、YouTube動画とショート動画を1本作るのに**これまで64時間**（8時間/日 × 土日2日 × 4週間）かけていました。当時の作業手順は以下の通りです。

1. 台本を考えます
2. VOICEVOX（無料の音声合成ソフト）で1行ずつ読み上げさせます
3. DaVinci Resolve（動画編集ソフト）でスライドと音声を並べます
4. Canva（デザインツール）でショート用に文言を入れます……

平日は本業で埋まっています。土日だけで作業すると、1本仕上げるのに1ヶ月かかります。これでは更新が止まるのも当然でした。

そこで、Zenn記事から動画・サムネイル・YouTubeショートまでを一気通貫で生成するパイプライン（処理を順番につなげた仕組み）を作りました。

![動画自動生成パイプラインの流れ：Zenn記事から台本、スライド・音声、動画合成を経てYouTube動画・ショート動画・サムネイルを出力](https://static.zenn.studio/user-upload/9dc9fecd0784-20261001.png)

| | Before(手動) | After(このパイプライン) |
|---|---|---|
| 台本作成 | 自分で構成を考えて書く | Claudeが記事から生成・自己採点・修正 |
| 動画 | DaVinci Resolveで作成 | コマンドラインで生成 |
| 音声 | VOICEVOXで1行ずつ読み上げ | 全セリフを自動合成、間も自動調整 |
| スライド | PowerPoint/Canvaで作成 | Pillow（Pythonの画像ライブラリ）で自動描画（4レイアウト+実物のコード/図） |
| 立ち絵・字幕 | 無し | 話者ごとに口パク・色分け字幕を自動合成 |
| BGM/SE | 無し | フェードイン/アウト付きで自動ミックス |
| サムネイル | Canvaで手動 | Geminiが背景・文字含めて丸ごと生成 |
| ショート動画 | Canvaで冒頭を切り出して手動編集 | シーン境界を検出して自動生成 |
| **更新頻度** | **月1回** | **月4回** |
| **所要時間** | **64時間**（8h×土日2日×4週間） | **15分未満**（再生成含む） |

## 動画自動生成パイプラインの全体像 — Claude・Gemini・VOICEVOX・ffmpegの役割分担

1つのAPIで完結させず、役割ごとに最適なツールを組み合わせています。

![動画自動生成パイプライン 全体アーキテクチャ](https://static.zenn.studio/user-upload/1c7d76cee26d-20260928.png)

- **Claude**: 台本・スライド内容・VOICEVOX用テキスト・概要欄をそれぞれ「生成→評価→修正」のループで作ります。評価担当のエージェントが80点未満と判定したら、フィードバックをもとに該当箇所だけ直して再評価します
- **Gemini**: スライドの背景イラストと、サムネイル・ショートの背景+文字を丸ごと生成します。加えて、後述する総合エージェントの整合性チェックをClaudeと独立に行うクロスチェック役も兼ねています
- **VOICEVOX ENGINE**: ローカルで起動したエンジンにHTTPで話者IDとテキストを渡して音声合成します
- **ffmpeg**: 動画・音声を加工する定番のコマンドラインツールです。音声の結合・字幕の焼き込み・立ち絵の口パクオーバーレイ・BGMミックス・最終合成をすべて担当します

## AI駆動開発をスムーズに進めるコツ：「完成形」を先に決める

今回は、AI駆動開発（AIにコードを書かせながら進める開発）が比較的スムーズに進みました。理由は「完成形」が最初から明確だったことだと思っています。自分自身が普段作っている動画そのものがゴールなので、「これで合っているか」を判断する基準が最初から自分の中にありました。

実際の開発の進め方は、動画を生成→アップロードしてClaudeに見てもらう→どこがおかしいかを具体的に伝える→直す、というループの繰り返しでした。

![開発の進め方：フィードバックループ](https://static.zenn.studio/user-upload/b060fa4df888-20260928.png)

「キャラクターと文字が被っている」「音声が途中で途切れている」「つむぎの口調が公式設定と違う」といった指摘を1つずつ入れていくことで、精度を上げていきました。ゴールが曖昧なまま「いい感じに作って」と頼むより、はるかに手戻りが少なかったです。ここから先は、その過程で実際に固まっていった設計判断を4つ紹介します。

## 設計判断1: AIの品質チェックは1つのAIに任せない（Claude×Geminiのクロスチェック）

台本・スライド・VOICEVOXテキストの整合性をチェックする「総合エージェント」を作りました。最初はClaude単独でスコアリング（点数付け）させていましたが、これには限界がありました。**1つのAIの採点をそのまま品質ゲート（合格・不合格を決める関門）にすると、そのAI自身の癖（見落としやすいパターン、逆に神経質になりすぎる箇所）がそのまま製品の挙動に出てしまいます**。

![総合エージェントの修正ループ設計](https://static.zenn.studio/user-upload/d028bba96201-20260928.png)

そこで、判定を担当AI(Claude)単独に任せず、別系統のAI(Gemini)にも同じ観点で独立にチェックさせ、**両方が一致して指摘した問題だけを「確認済み」として修正ループに反映する**設計に変更しました。

![Claude×Geminiのクロスチェック：両方が同じ問題を指摘したときだけ修正ループへ進む](https://static.zenn.studio/user-upload/07bc3ca8cb03-20261001.png)

本番投入前に、既知の不整合(話者の入れ替え、台本とスライド/VOICEVOX間の数値の食い違いなど)をわざと注入して検証しました。無改変データでは両者とも誤検知なく、注入した不整合はどちらのAIも見落としなく検出できました。`GEMINI_API_KEY`が未設定、またはGemini呼び出しに失敗した場合は、従来通りClaude単独チェックへ自動でフォールバック（代わりの方法に切り替えること）します。

## 設計判断2: AIエージェントの修正ループが止まらない問題と解決策

総合エージェントは当初、スコアが基準点以上でも`issues`（指摘事項のリスト）が1件でも残っていれば修正ループを継続する設計にしていました。これは「スコアだけで判定すると、まとめスライドとエンディングスライドのscene_numberが重複している、台本に無い数値がスライドにだけ出典不明のまま追加されている、といった軽微だが実質的な不整合がそのまま素通りしてしまう」という、実際に起きた不具合を踏まえた対策でした。

ただしこの条件は裏目にも出ました。issueの重要度を判定せず「1件でもあれば直す」という一律の扱いだったため、言い回しレベルの些末な指摘や、Claude自身の癖による指摘のためだけに、毎回`MAX_REVISION_LOOPS`(3回)フルで修正ループが回ってしまうケースが出てきました。

![修正ループの改善前と改善後：2つのAIが一致した指摘だけを反映して無駄なループを減らす](https://static.zenn.studio/user-upload/3d4d824d2d1b-20261001.png)

結果的に、この問題は設計判断1のデュアルAI一致方式でかなり緩和されました。言い回しレベルの些末な指摘は大抵どちらか一方のAIしか拾わないため、「両方が一致した指摘だけ反映する」というフィルタが、そのまま「重要度の低いissueで無駄にループが回る」問題のフィルタとしても機能したためです。1つの設計判断が、別の場所で起きていた問題も副次的に解決した形になります。

## 設計判断3: ショート動画の切り出しは推測せず、JSONのシーン境界を使う

ショート動画は「冒頭60秒あたりのセリフの切れ目で切る」という方式で作っていました。BGMを使っていると、セリフとセリフの間の無音がBGMの音でかき消されて検出できませんでした。結局60秒ぴったりで切れてセリフが途中で終わる、という不具合が起きました。

![ショート動画の切り出しとBGM誤爆](https://static.zenn.studio/user-upload/0711977eaa49-20260928.png)

無音検出という「推測」に頼るのをやめました。動画生成時に「シーン1は何秒から何秒まで」という正確な境界をJSON（データを書き留めるテキスト形式）で保存しておき、ショート生成時はそれを読むだけにする方式に変えて解決しました。

![ショート動画の切り出し：無音検出による推測から、JSONのシーン境界を読む方式へ](https://static.zenn.studio/user-upload/8f1b02e6e1e5-20261001.png)

これは動画生成に限らない教訓だと思っています。**パイプラインのどこかの工程が持っている「正確な情報」を、別の工程で推測し直そうとしていないか**は、AIエージェント設計全般でチェックする価値があるポイントです。

今回の場合、台本の構造そのものがシーン境界という正確な情報を最初から持っていたのに、それを使わずに音声波形から無音区間を当てにいっていました。情報の出所を1つ遡るだけで、推測に頼らない設計に変えられました。

## 設計判断4: Geminiでキャラクター画像を安定生成する — 参照画像を渡すimage-to-image

サムネイル生成では、Geminiに「つむぎ」「ずんだもん」が登場するサムネイルを作らせていました。最初はプロンプト（AIへの指示文）に「つむぎ(立ち絵風の女の子)とずんだもん(緑色のずんだ餅キャラ)が驚いた顔をしている」のように**文章で見た目を説明**していました。

結果、生成のたびにデザインが微妙に違うキャラクターが出てきたり、ひどい時は指示にない人間の顔を勝手に描いてしまったりしました。プロンプトの説明をどれだけ詳しくしても、「文章から見た目を再現する」というAIの推測に頼っている限り再現性は上がりませんでした。

これも設計判断3(シーン境界)と根っこは同じ問題でした。**パイプラインは、キャラクターの正確な見た目そのもの(立ち絵素材の画像ファイル)をすでに持っている**のに、それを使わずわざわざ文章に変換してからGeminiに渡し、Gemini側でまた画像に戻すという「情報を一度劣化させてから推測させる」遠回りをしていました。

![キャラクター生成：文章による見た目の説明から、参照画像をそのまま渡す方式へ](https://static.zenn.studio/user-upload/26f1c965ebe3-20261001.png)

そこで、立ち絵素材の画像をプロンプトの文章と一緒に`contents`へ直接渡す方式（image-to-image：参照画像をもとに新しい画像を作る方法）に変えました。Nano Banana系（Geminiの画像生成モデル）はこれを見て、キャラクターのデザイン・配色・線画のタッチを保ったまま新しい構図に描き直せます。あわせてプロンプト側にも「参照画像のデザインを忠実に使い、別人や人間の顔に描き替えないこと」と明記し、念押ししました。

見た目の再現性が要るところでは、テキストによる説明ではなく実物のデータ(この場合は画像)をAIに直接渡す。設計判断3と合わせて、「推測より構造化データ」という今回のパイプライン全体を貫く教訓が、テキスト生成だけでなく画像生成でも同じ形で効いた例です。

## 動画自動生成で踏んだ不具合と対処法（ffmpeg・VOICEVOX・JSON）

ここからは、個別の不具合と対処です。設計判断というほど大きな話ではありませんが、同じようなパイプラインを作る人にはそのまま役立つかもしれません。

### ffmpegのconcatデマクサーが、解像度の違う画像を無視する

サムネイルを動画の冒頭に使う機能を作ったとき、なぜかサムネイルが表示されずいきなり2枚目のスライドから始まる不具合が起きました。

原因はffmpegのconcat（複数の素材を連結する機能）の挙動でした。**先頭の画像だけ他と解像度が違うと、実質その画像を無視してしまう**という仕様です。サムネイルは1280x720、本編のスライドは1920x1080でした。

![ffmpeg concatデマクサーの解像度問題](https://static.zenn.studio/user-upload/9a9cd8030101-20260928.png)

scaleフィルタ（ffmpegの拡大縮小機能）を挟んでも直らず、結局「事前に動画と同じ解像度にリサイズしてから渡す」という力技で解決しました。

### 音声だけが2秒早く進んでいた

字幕・スライドの切り替わり・音声の再生タイミングがすべてズレる不具合がありました。原因は、動画の冒頭2秒は無音のタイトル画面のはずなのに、**音声トラックにはその2秒の無音を入れ忘れていた**ことでした。字幕とスライドは「2秒後から本編が始まる」という前提で計算していたのに、音声だけ0秒から喋り始めていました。

![音声だけが2秒早く進んでいた](https://static.zenn.studio/user-upload/628be2f130f8-20260928.png)

実際に477.2秒の映像に対して音声が474.88秒しかない、という差分から発覚しました。音声・字幕・映像のタイミングをすべて同じ「基準時刻の積み上げ」から計算するように直して解消しました。

### VOICEVOXの読み間違いは読み替え辞書で対処する

読み間違いが頻発しました。例えば「架空の乗客データ」が「かからの乗客データ」と読まれます。「空の箱」も「そらの箱」と読まれます。日本語は同じ漢字でも文脈によって読みが変わるので、TTS（テキスト読み上げ）にはよくある問題です。

読み替え辞書（「この文字列はこう読ませる」という変換表）を作って対処しました。ただ、単純に「値」を「あたい」に全置換すると「数値」「戻り値」まで壊れる、といった別の不具合も踏みました。結局「この値」「その値」のような、単独用法と判断できる完全なフレーズ単位でしか安全に置換できないという結論になりました。

![VOICEVOXの読み間違いと読み替え辞書](https://static.zenn.studio/user-upload/b7f55c800176-20260928.png)

### VOICEVOX「春日部つむぎ」のキャラクター設定が台本とズレていた

VOICEVOXの「春日部つむぎ」は公式に「埼玉の高校に通う18歳のギャル、一人称は『あーし』」という設定です。生成された台本では「言い得て妙」のような硬い言い回しを喋らせてしまっていました。

![キャラクター設定のズレを修正するフロー](https://static.zenn.studio/user-upload/45cfb29d01c4-20260928.png)

キャラクター設定をちゃんと調べて台本エージェントのプロンプトに反映し直しました。地味ですが、こういう「キャラクターの一貫性」はVOICEVOX系コンテンツでは軽視できない部分だと思います。

### Claudeが返す「JSON」は、dict（辞書型）とは限らない

台本エージェントから総合エージェントまで、全エージェントが「JSON形式のみを返して」とClaudeに指示し、共通ヘルパー`call_json()`でパース（文字列をプログラムで扱えるデータに変換すること）しています。ここで「`json.loads()`が例外を投げなければOK」という判定にしていたため、構文的には正しいJSON(トップレベルが配列や文字列など)でも、想定していた`dict`でなかった場合にそのまま呼び出し元へ返してしまいました。その結果、後続の`result.get("score")`のような呼び出しでAttributeError/TypeErrorが起きて、パイプライン全体が落ちる不具合がありました。

```python
# 改善前：パースできればOKとしていた
parsed = json.loads(text)
return parsed  # 配列や文字列でもそのまま返ってしまう

# 改善後：期待する型(dict)かも確認する
parsed = json.loads(text)
if isinstance(parsed, dict):
    return parsed
# dictでなければ「パース失敗」と同じ扱いにして、Claudeへ再試行を依頼する
```

「JSONとしてパースできるか」と「呼び出し元が期待している形(dict)になっているか」は別問題なのに、同じチェックだと思い込んでいたのが原因でした。パース後に`isinstance(parsed, dict)`を確認し、falseなら既存の「パース失敗時にClaudeへ再試行を依頼する」パスに合流させるよう修正しました。AIに「JSON形式のみ返して」と指示しても、それは構文が正しいことの保証にしかならず、期待した型になっている保証にはならない、というのは地味に見落としがちなポイントです。

## 導入結果: 15分の内訳はAPI待ちだけ

パイプラインを本番投入した結果、動画制作は64時間→15分未満、更新頻度は月1回→月4回になりました。この15分のほとんどはClaude・GeminiのAPI呼び出しとffmpegのレンダリング待ちで、作業中に自分の手が止まる工程はほぼありません。手作業の時間そのものがなくなったことで、土日にまとまった時間が取れない週でも更新を止めずに済んでいます。

## まとめ: AIエージェント設計の教訓は「推測より構造化データ」

今回の設計判断を1枚にまとめると、次の図のようになります。

![まとめ：推測に頼る設計を、正確なデータを使う設計に置き換える](https://static.zenn.studio/user-upload/2c0aab800981-20261001.png)

今回いちばんの収穫は、実際に踏んだ不具合のほとんどが「コーディングそのもの」ではなく「何が起きているのかを疑い、検証し直す」作業だったことです。特に、品質ゲートを1つのAIに任せないという判断は、このパイプラインに限らず「AIによる自己評価をそのまま信用しない」という考え方として、他のエージェント設計にもそのまま持ち込めると思っています。

今後は、このパイプラインで作れる論文紹介系の動画を軸に更新頻度を維持しつつ、より作り込みが必要なハンズオン動画にじっくり時間をかける、という二段構えの運用を試していく予定です。
